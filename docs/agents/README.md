# AIエージェント開発ワークフロー

ebirogue を Claude Code（Pro）と Codex（Plus）で並列開発し、BOT による自動テストプレイで品質とバランスを検証するための運用ルールです。
個別タスクの指示書はこのフォルダの各ファイルにあります。プロジェクト全体の規約は従来どおり `AGENTS.md` が正本です。

## 基本方針

1. **AI にゲームを1ターンずつ遊ばせない。** LLM の利用枠はコードを書く・レポートを読む作業にだけ使う。
   テストプレイはルールベースの BOT がヘッドレス（描画なし）で CPU 上で大量に行い、利用枠を消費しない。
2. **合否は機械判定にする。** 各タスクは「gofmt・2系統のテスト・BOT スモークテストで不変条件違反ゼロ」を満たして完了とする。
3. **AI に渡すのは集計レポートだけ。** 生ログではなく、クリア率・死因・バグ一覧（再現シード付き）の Markdown を読ませる。

## クリア条件と難易度（確定仕様）

| 難易度 | クリア条件 |
|---|---|
| 初級 | 10階のボスを倒す |
| 中級 | 20階のボスを倒す |
| 上級（標準） | 30階のボスを倒す |

- ボスは難易度に関係なく 10・20・30 階に配置する。目標階より手前のボスを倒しても冒険は続く。
- 難易度は冒険開始時に選び、冒険データ（`SaveData`）に保存する。冒険の途中で変更できない（`GameSettings` には入れない）。
- BOT のレポートは難易度ごとにクリア率を集計する。

## フェーズと担当

| フェーズ | 内容 | 担当 | 並列度 |
|---|---|---|---|
| 0 | 基盤：乱数集約、入力抽象化、ヘッドレス実行、死因記録、クリア判定の骨格、BOT・検査・レポート | Claude Code | 直列（`phase0-foundation.md`） |
| 1 | 移動系の罠／ダメージ系の罠／ボス3体／難易度選択とクリア画面 | Codex（統合は Claude Code） | 2〜3本ずつ（`wave1-*.md`） |
| 2 | 状態異常の共通化→新状態異常、装備・所持品の罠、敵が罠を踏む、1〜30階の出現テーブル、モンスターハウス、キー設定 | 両方 | `wave2-backlog.md` |
| 3 | 店、合成、特殊地形、図鑑 | 両方 | 未計画 |

フェーズ0が終わるまで並列実装は始めない。フェーズ0は多くのファイルに触れるため、並列タスクと同時に進めるとマージ衝突が増える。

## 役割分担と利用枠の節約

- **Claude Code（Pro）**: 設計、フェーズ0、各ブランチの統合とレビュー、シミュレーションレポートの分析。
  - Pro の利用枠は claude.ai のチャットと共有される。`/status` で残量を確認する。
  - レポート要約やログ調査のサブエージェントは `model: haiku` を指定する。
  - 並列作業は `claude --worktree <名前>` またはサブエージェントの `isolation: worktree` で作業場所を分ける。
- **Codex（Plus）**: フェーズ1以降の各担当を実装する。Claude とは別の利用枠なので、実装量の多い担当はこちらへ回す。
- **CPU（無料）**: BOT のテストプレイとファジング。夜間や外出中に回す。
- 5時間枠の目安は「並列2〜3本」。大きい担当は枠の開始直後に投入する。
- エージェントには大きいファイル（`content_cards_test.go`、`itemeffects.go`、`items.go`）を丸ごと読ませず、`grep` で該当箇所を探させる。

## 並列作業のルール（AGENTS.md の一部規則を並列時のみ上書き）

1. **ブランチで作業する。** 各担当は `agent/<タスクID>` ブランチを作り、master へ直接コミット・プッシュしない。
2. **ドキュメントは統合時にまとめて更新する。** 担当エージェントは `AGENTS.md` と `IMPLEMENTED_FEATURES.md` を編集しない。
   代わりに PR の説明、またはブランチ内の `docs/agents/done/<タスクID>.md` に「IMPLEMENTED_FEATURES.md への追記案」と「AGENTS.md から削除するロードマップ項目」を書く。
   統合担当（Claude Code）がマージ時に1回で反映する。
3. **ID は下表の割り当てを使う。** 割り当て外の ID を使わない。
4. **共有ファイルへの変更は最小限にする。** `main.go` の `NewGame`、`draw.go` の画像分岐、`savegame.go` など複数担当が触る箇所は、追記だけにとどめ既存行を並べ替えない。
5. **完了条件**（すべて必須）:
   - `gofmt -w` 済み
   - `go test -tags test ./...` と `go test ./...` が成功
   - フェーズ0完了後は `go test -run TestSimSmoke -count=1 .` で不変条件違反ゼロ
   - 新しい乱数処理は `g.randIntn()` などの Game の乱数源経由で、同じシードで結果が再現する

### ID 割り当て表

| 種類 | 既存 | 割り当て |
|---|---|---|
| 罠 | 0〜11（wave1-A: 5〜7、wave1-B: 8〜11 は統合済み） | wave2 装備・所持品系: 12〜14 予約 |
| 敵 | 0〜41 | wave1-C ボス: 42（10階）、43（20階）、44（30階） |
| アイテム | 0〜70 | wave2 以降: 71〜 を担当ごとに割り当てる |

罠は現在スライスの添字が ID になっているため、フェーズ0の P0-1 で明示 ID 付きのテーブルへ変更する。

## 画像

- エージェントは新しい画像を Go や Python のスクリプトで 30x30 の透過 PNG として仮作成してよい（輪郭がはっきりした単純な図形、四隅は透明）。
- 仮画像を使った場合は、`docs/agents/done/<タスクID>.md` に「差し替えが必要な画像」として列挙し、統合時に AGENTS.md の残タスクへ移す。

## 外部コードの参照ポリシー

このリポジトリは公開されているが、LICENSE ファイルがない（第三者が再利用できる条件が未定義の状態）。

- **コードを取り込んでよいもの**: MIT / BSD / ISC / Apache-2.0 など寛容なライセンスのもの。例: anaseto の Harmonist・Boohu と gruid（Go、ISC）、rot.js、libtcod。
  取り込んだ場合は著作権表示とライセンス文を `THIRD_PARTY_NOTICES.md` に残す。
- **仕様の参考にとどめるもの**: DCSS（GPLv2+）、Brogue CE（AGPLv3）、Angband（GPLv2）、NetHack（NGPL）、SFC シレン wiki。
  コードの翻訳・移植はしない。参照する場合は2段階にする: エージェント1が挙動を自分の言葉で `docs/specs/<名前>.md` にまとめ、エージェント2はその仕様書だけを見て実装する。

## クラウド（Linux）で Codex を動かす場合

環境構築スクリプトに Go 1.24 と Ebitengine の依存ライブラリを入れる。v2.8 系は cgo でビルドするため、開発用パッケージが必要になる場合がある。

```bash
sudo apt-get update
sudo apt-get install -y libgl1-mesa-dev xorg-dev libasound2-dev pkg-config
go test -tags test ./... && go test ./...
```

`go test ./...` がビルドエラーになる場合は、エラーに出たヘッダーのパッケージを追加する。
