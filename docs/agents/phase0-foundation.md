# フェーズ0: テスト基盤（Claude Code 用作業指示書）

担当: Claude Code（master ブランチで直列に進める）
前提: `AGENTS.md` と `docs/agents/README.md` を読んでから始める。
進め方: 下の P0-1〜P0-8 を順番に、1ステップ1コミットで進める。各ステップの完了条件を満たしてから次へ進む。
共通の完了条件: `gofmt -w`、`go test -tags test ./...`、`go test ./...` が成功すること。

このフェーズの目的は「同じシードと同じ入力なら必ず同じ結果になるゲームを、描画なしで BOT が何千回も遊べる状態」を作ることです。
ロードマップの Priority C（シード、冒険結果の保存、リプレイ、F1 デバッグ分離）と、クリア条件・難易度の骨格もここで実装します。

---

## P0-1 並列作業の下準備（ID テーブルの整理）

- `mapTrapTemplates` をスライスの添字ではなく、明示的な ID を持つテーブルにする（例: `map[int]mapTrapTemplate` または要素に `ID` フィールド）。既存の罠は ID 0〜4 のまま。
- `savegame.go` の `mapTrapTemplateID` を明示 ID ベースにする。既存セーブとの互換を保つ。
- `createItem` と `createEnemy` の `rand.Intn(len(...))` をやめ、「ランダム出現の対象 ID 一覧」から選ぶ形にする。ID に欠番があっても動き、ボス（後述の `IsBoss`）は対象外にできるようにする。
- 罠・敵・アイテムの ID が重複せず、全テンプレートが生成できることを確認するテストを追加する。

完了条件: 既存の動作が変わらず、ID に欠番を作ってもランダム生成が壊れないことをテストで確認できる。

## P0-2 乱数の集約とシード

- `Game` に `seed int64` と `rng *rand.Rand` を持たせる。グローバルの `rand.Intn` などの呼び出し（現状13ファイル・約78か所）をすべて `g.rng` 経由にする。
  - `Game` を受け取らない関数は、`intn func(int) int` などの引数で乱数源を注入する（`damageRandInt` や `rollXxx(intn)` の既存パターンに合わせる）。
  - パッケージ変数の乱数源は、複数のゲームを同時にシミュレートするときに競合する。可能な限り `Game` 単位に移す。
- フロア生成用とターン進行用で乱数系列を分けるかを検討する（分けると、プレイの違いでマップが変わらず再現性が高い）。
- シードと乱数の状態を `SaveData` に保存する。`saveDataVersion` を上げる。
- HUD またはメニューに現在のシードを表示し、同じシードで再挑戦できるようにする（ロードマップ Priority C）。

完了条件: 同じシードでフロアを生成すると、マップ・敵・アイテム・罠が完全に一致するテスト。`go test -race` で乱数の競合が出ない。

## P0-3 入力の抽象化

- `input.go` などにある `ebiten.IsKeyPressed` と `inpututil.IsKeyJustPressed` の直接呼び出しを、`Game` が持つ `InputSource` 経由に置き換える。

  ```go
  type InputSource interface {
      Pressed(k Key) bool
      JustPressed(k Key) bool
      Update() // フレームの区切り
  }
  ```

  - 本番用: Ebiten をラップする実装（`!test` ファイル）。
  - テスト・BOT 用: スクリプトでキーを押下・解放する仮想入力の実装（タグなしファイル）。
- `Key` はゲーム内の論理キー（上・下・左・右・Shift・Z・X・A・C・D・Space・F・S・N・H・L など）として定義する。これが将来のキー設定（ロードマップ Priority A）の土台になる。
- 入力をフレーム番号付きで記録・再生できるようにする（リプレイ、ロードマップ Priority C）。

完了条件: 仮想入力で「右へ3歩移動して正面を攻撃する」などのシナリオを再生するテストが通る。実際のゲームの操作感は変わらない（手元で起動して確認）。

## P0-4 ヘッドレス実行と演出スキップ

- 画像を読み込まずに `Game` を作る `newHeadlessGame(seed int64, difficulty Difficulty) *Game` を用意する。`Draw` は呼ばない。
- `fastForward` モードでは、Action の `Duration`、フェードイン・フェードアウト、攻撃アニメーション、死亡後の待ち時間をゼロとして扱い、`Update()` を何回呼んでも実時間に依存しない。
- 1フレーム進める `StepFrame()` と、入力を受け付けられる状態まで進める `RunUntilInputReady(maxFrames int) error` を用意する。`maxFrames` を超えたら操作不能（ソフトロック）としてエラーを返す。
- 死亡時の `resetGame` による自動リスタートは、ヘッドレスでは行わず「冒険終了」として止める。

完了条件: ヘッドレスで1000ターン分を数秒以内に進められる。ウィンドウなしの `go test ./...` で動く。

## P0-5 死因の記録と冒険結果

- 最後にプレイヤーへダメージを与えた原因を `lastDamageSource` として記録する。原因の種類: 敵の通常攻撃（敵 ID）、敵の特殊攻撃・遠距離攻撃（敵 ID と種類）、罠（罠 ID）、餓死、毒、自爆系カード、その他。
  - ダメージ処理が `damage.go` の `rollDamage` 系と、罠・状態異常の直接減算に分かれているので、すべての経路を確認する。
- 冒険の結果を `RunResult` 構造体にまとめる: シード、難易度、クリア可否、到達階、ターン数、レベル、死因、所持品、装備。
- 死亡時の画面に死因を表示する（例: 「10階で 火吹きイカ の炎にやられた」）。
- 結果を保存する（ネイティブ版はファイル、WASM 版は `localStorage`。`storage.go` の4関数経由）。

完了条件: 敵・罠・餓死・毒それぞれで死亡したときに、正しい死因が記録されるテスト。

## P0-6 クリア条件と難易度の骨格

- `Difficulty`（初級・中級・上級）と `goalFloor(d Difficulty) int`（10・20・30）を定義する。難易度は `SaveData` に保存する。
- 敵定義に `IsBoss bool` を追加する。ボスはランダム出現と `MonsterLevelUpTable` の対象外にする（ボスは AGENTS.md の「上位種も同時に追加」の例外）。
- 10・20・30階をボス階とし、ボスを1体配置する。**このステップでは仮のボスでよい**（既存の強い敵の能力値を上げ、`IsBoss` を付けたもの）。本物のボスは wave1-C で作る。
- ボス階の階段は、ボスを倒すまで使えないようにする。
- 目標階のボスを倒したら `cleared` を立て、冒険を「クリア」で終了する。簡単なクリアメッセージを表示する（本格的なクリア画面は wave1-D で作る）。
- 30階のボスを倒した後に31階以降へ進めないこと。

完了条件: ヘッドレスで「ボス階へ移動→ボスを倒す→難易度に応じてクリア／続行」が判定されるテスト。

## P0-7 BOT・不変条件の検査・レポート

### BOT

- ゲーム状態を直接読み（ホワイトボックス）、仮想入力でキーを押して操作する。
- メニュー操作は「アイテム n を使う」「足元のアイテムを拾う」などの高レベル行動を、キー操作列に変換するヘルパーを通して行う。本物のメニュー経路をテストするため、関数を直接呼んで済ませない。
- 移動は経路探索（BFS またはダイクストラマップ）で、未探索の部屋や階段、アイテムへ向かう。
- 性格（ペルソナ）を複数用意する:
  - `aggressive`: 見えた敵に向かい、HP が低くても戦う
  - `cautious`: HP 40% で回復アイテムを使い、危険な敵から逃げる
  - `itemUser`: カード・杖・投擲を積極的に使う
  - `diver`: 階段へ直行する
  - `random`: ランダムに入力する（バグ探し用）

### 不変条件（毎ターン検査）

- `RunUntilInputReady` が上限フレーム内に戻る（ソフトロックしない）
- プレイヤーと敵が壁の中にいない（壁抜けする敵を除く）、敵同士・敵とプレイヤーが同じマスにいない
- HP は 0 以上かつ最大 HP 以下、満腹度は 0〜最大値、所持品は上限以下
- 敵とアイテムの座標がマップ範囲内
- panic しない（発生したら recover して、シード・ペルソナ・入力履歴を保存する）
- ランダムなターンで中断セーブ→再開を挟み、`buildSaveData` の結果が保存前と一致する

### 実行方法とレポート

- `sim_test.go` に2つのテストを用意する:
  - `TestSimSmoke`: 少数のシード（例: 20シード × 各ペルソナ × 500ターン）。`go test ./...` で毎回実行し、マージの合否判定に使う。
  - `TestSimBatch`: `-sim.runs` などのフラグを付けたときだけ実行する大規模版。例:

    ```bash
    go test -run TestSimBatch -count=1 -timeout 0 . -args -sim.runs=1000 -sim.difficulty=all -sim.out=reports
    ```

- 出力: `reports/sim-<日時>.json`（全結果）と `reports/sim-<日時>.md`（集計）。集計 Markdown には次を入れる:
  - 難易度×ペルソナ別のクリア率、平均到達階、平均ターン数
  - 階層別の死亡率、死因の上位（敵・罠・餓死など）
  - 不変条件違反とソフトロックの一覧（再現用のシード・ペルソナ・ターン番号付き）
  - 前回のベースライン（`reports/baseline.json`）との差分
- 失敗ケースは `go test -run TestSimReplay . -args -sim.seed=<シード> -sim.persona=<名前>` で1件だけ再現できるようにする。
- `reports/` は `baseline.json` 以外を `.gitignore` に入れる。
- goroutine で並列に実行する。P0-2 でパッケージ変数の乱数を残した場合は、プロセスを分けて並列化する。

完了条件: `TestSimSmoke` が数十秒以内に終わる。`TestSimBatch` で1000回分のレポートが出る。意図的に入れたバグ（例: HP が最大値を超える）を不変条件が検出する。

## P0-8 ファジング・デバッグ分離・テストファイル分割

- `FuzzInputSequence`: バイト列を入力の列に変換して遊ばせ、不変条件を検査する Go のファズテスト。
  `go test -fuzz=FuzzInputSequence -fuzztime=30m .` で長時間回せるようにする。
- F1 デバッグ処理を通常プレイから分離する（`debug` ビルドタグ、または開発者設定で有効化。ロードマップ Priority C）。
- `content_test.go`（約94KB）を、アイテム・カード・敵・罠などの分野別ファイルに分割する（エージェントの読み込み量とマージ衝突を減らすため）。

完了条件: ファジングを10分回して違反がないか、見つかった違反を修正済み。
